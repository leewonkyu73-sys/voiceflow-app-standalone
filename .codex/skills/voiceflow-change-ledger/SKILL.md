# VoiceFlow 무회귀 변경 가드

VoiceFlow 변경 전에 이 파일과 [누적 장애 원장](references/ledger.md)을 끝까지 읽는다. 설계·복구·대규모 수정이면 [회귀 방지 근거와 실행 기준](references/regression-guard.md)도 읽는다.

## 절대 불변 조건

- 사용자가 품질 개선·업그레이드·새 방식 도입을 명시적으로 요청하지 않은 오류 수정은 마지막으로 실제 작동이 확인된 기존 구현을 기준으로 한다.
- 오류 수정만 요청된 경우 신규 아키텍처, 새 Provider, 유료 API, 자동 fallback, 우회 페이지 또는 기본 실행 경로 변경을 제안하거나 적용하지 않는다.
- 업그레이드를 명시적으로 요청받아도 기존 정상 경로를 유지한 채 후보를 기본 OFF로 분리하고, 품질·비용·영향·복구 방법을 비교 보고한 뒤 승인받기 전에는 기본값으로 전환하지 않는다.
- 기존에 실제 기기에서 정상 확인된 기능·성능·UI를 새 기능 때문에 낮추지 않는다.
- 기능 삭제, 숨김, 우회 화면 추가, 원문 반환을 성공으로 간주하지 않는다.
- 음성→원문→선택 언어 번역 중 하나라도 실패하면 화상·외부음성·Zoom·관리자 확장을 중단한다.
- DB·DNS·Secret·관리자·NFC·업무 기능은 명시적 범위가 아니면 변경하지 않는다.
- CI 성공, 운영 자산 존재, 실제 기기 성공을 서로 대체하지 않는다.

## 변경 전 필수 게이트

1. 마지막 정상 기준을 커밋 SHA와 실제 확인 기능으로 고정한다. 실제 확인 증거가 없으면 “추정 정상”으로 표시한다.
2. 변경 파일뿐 아니라 생성 스크립트, 로더, CSS, 서비스워커, API, 배포 검증기까지 소비자를 추적한다.
3. 영향표를 작성한다: 변경 기능, 직접 소비자, 간접 영향, 보호할 정상 기능, 관측 지표, 복구 파일.
4. 핵심 경로와 부가기능을 분리한다. 동일 DOM·마이크 스트림·상태 객체·렌더 함수에 새 기능을 직접 결합하지 않는다.
5. 한 PR에는 한 원인만 넣는다. 서로 독립적인 변경은 분리한다.
6. `Golden SHA → 변경 직전 SHA → 후보 SHA → 실제 운영 SHA`를 각각 확인한다. 브랜치 HEAD나 배포 성공을 운영 SHA로 추정하지 않는다.
7. 아래 보호 자원의 단일 소유자를 적는다. 소유자가 겹치면 설계 단계에서 병합을 차단한다.
   - 마이크·화면/시스템 오디오 스트림
   - `MediaRecorder`·브라우저 STT·서버 STT fallback
   - `state.media`와 녹음/인식 타이머
   - 대화 DOM·전체 `render()`·`postCaption()`·번역 API
8. 변경 전 동일 입력으로 최소 기준 검사를 실행한다: 직접입력 원문/번역, 모바일 마이크 원문, PC 마이크 원문, 화상 참가자 유지, 저장·재접속. 실행할 수 없는 항목은 `UNVERIFIED`이며 병합 판단에 명시한다.
9. 생성 패치 체인은 수정 패치의 앞·뒤 소비자와 최종 생성물 해시/계약을 비교한다. 문자열 표식만 존재하는 검사는 사용자 결과 검사를 대체하지 않는다.
10. 요청을 `기존 기능 복구`와 `명시적 업그레이드` 중 하나로 분류한다. 복구 요청이면 기존 정상 구현의 최소 복원 외 변경을 차단한다.
11. 새 방식 후보가 필요할 때는 기존 대비 정확도·지연·비용·권한·지원 기기·운영 의존성·실패 시 영향·롤백을 먼저 비교한다. 하나라도 미확인이면 기본 경로로 승격하지 않는다.
12. 비용이 생기는 API나 서버 처리로 무료·로컬·브라우저 경로를 자동 대체하지 않는다. 사용자에게 예상 비용과 호출 조건을 알리고 명시적 승인을 받은 기능에서만 사용한다.

## Provider 비용·사용량 관측 기본 게이트

- 장애 분석 때 Provider의 `credential`, `binding`, `live response`, `authentication`, `model`, `quota/billing`, `usage/cost`를 별도 항목으로 확인한다.
- 앱이 기록한 요청·입력/출력 토큰·오디오 초·추정비용과 Provider가 확정한 청구비용을 구분한다. 추정값에는 반드시 `예상`을 표시한다.
- OpenAI 조직 Usage/Costs API는 조직 관리자 권한이 있는 별도 Admin Key가 있을 때만 서버에서 조회한다. 일반 프로젝트 API Key로 잔여 크레딧을 조회할 수 있다고 가정하지 않는다.
- Admin Key를 브라우저·로그·DB 평문·채팅에 노출하지 않는다. 구성되지 않았으면 Hub에 공식 Usage/Billing 링크와 마지막 실응답 오류 분류만 표시한다.
- `429/quota/credit/billing`은 코드 회귀와 분리해 `PROVIDER BILLING BLOCKED`로 기록한다. 이 상태에서 음성→원문·번역을 코드 수정으로 반복 해결하지 않는다.
- Hub 사용량 화면은 최소한 Provider, 소비 앱, 기간, 요청 성공/실패, 오디오 시간, 입력/출력 토큰, 예상비용, 확정비용, 마지막 성공/실패 시각, 오류 분류, 데이터 출처를 표시한다.

## 반복 장애 자동 중단과 기존 성공 복구

다음 중 하나라도 발생하면 패치·신규 구현·리팩터링·배포를 즉시 중단한다.

- 동일 사용자 증상이 두 번 이상 재발함
- 한 수정이 음성, 번역, 화상, 채팅 중 다른 정상 기능을 악화함
- 일주일 또는 세 개 PR 이상 핵심 장애가 계속됨
- DEVICE 실패인데 CI·운영 자산만 성공함
- 마지막 실제 정상 커밋과 기기 증거가 불명확함

중단 후에는 새 방식이나 우회 페이지를 만들지 않는다. 다음 순서로만 복구한다.

1. 사용자가 실제로 정상 확인한 가장 최근 커밋·기기·브라우저·시나리오를 찾는다. 자동검사만 성공한 커밋은 정상 후보일 뿐 Golden 기준이 아니다.
2. 정상 후보와 최초 실패 후보 사이를 Git 이분 탐색하거나 커밋별 동일 시나리오로 비교해 최초 회귀 변경을 확정한다.
3. 외부 음성처럼 이미 구현된 기능은 새로 만들지 않고 마지막 정상 파일·함수·생성 스크립트를 우선 재사용한다.
4. 전체 롤백이나 새 코어 생성 전에 최초 회귀를 만든 최소 파일·함수만 복원할 수 있는지 확인한다.
5. 원인이 확정되기 전에는 운영 코드, DB, DNS, Secret, Provider 설정을 변경하지 않는다.
6. Golden 기준, 후보 결과, 최초 실패, 복원 파일, DEVICE 결과를 원장에 남긴 뒤에만 신규 개발을 재개한다.

사용자가 기존 성공 구현을 찾으라고 지시한 경우 신규 아키텍처, 별도 페이지, 대체 Provider 또는 새 입력 경로를 제안·구현하지 않는다. 기존 성공 구현이 기술적으로 복구 불가능하다는 증거가 있을 때만 이유와 영향을 보고하고 승인을 받는다.

## 문제 발생 시 스킬 갱신

새 장애나 회귀가 확인되면 작업을 끝내기 전에 [누적 장애 원장](references/ledger.md)을 업데이트한다. 동일 유형이 다시 발생할 수 있으면 이 SKILL의 의사결정 규칙이나 관련 회귀검사도 함께 강화한다.

원장 항목에는 최소한 다음을 기록한다.

- 사용자에게 보인 정확한 증상과 최초 발생 시점
- 마지막 실제 정상 SHA와 최초 실패 SHA
- 재현 기기·브라우저·입력·기대 결과
- 확인된 원인과 영향을 받은 소비자
- 시도했으나 실패한 수정과 되돌린 변경
- 최종 최소 수정 또는 복원
- SOURCE, CI, DOCKER, DEPLOY, OPERATING, DEVICE의 개별 상태
- 재발 시 자동 중단 조건과 정확한 복구 지점

원인 미확정, Provider 미확인, 실제 기기 미검증은 그대로 미확인으로 기록한다. 추정 원인을 확정 사실처럼 스킬에 넣지 않는다.

## 작업별 모델 추천

작업을 시작할 때 현재 사용자 지시, 최근 대화, 장애 기간, 변경 범위, 운영 위험, 필요한 검증을 읽고 모델을 먼저 추천한다. 모델 이름만 제시하지 말고 선택 이유, 비용·속도·정확도의 상대적 이점, 더 강한 모델로 올리거나 낮춰도 되는 조건을 짧게 설명한다.

- **Sol**: 반복 회귀, 근본 원인 분석, 여러 커밋·서비스·CI·운영 상태 비교, 복잡한 코드 수정, 보안·데이터·배포 위험, 실제 정상 기준이 불명확한 작업에 사용한다. VoiceFlow 핵심 음성·번역·화상 복구와 Golden 기준 확정은 Sol을 기본 권장한다.
- **Terra**: 원인과 정상 기준이 확정된 뒤의 단일 원인 최소 수정, 분리된 모듈 구현, 명확한 테스트 실행, 문서·원장 갱신에 사용한다. Sol이 만든 영향표와 복구 지점이 있어야 핵심 운영 수정에 Terra를 권장할 수 있다.
- **Luna**: 변경 없는 상태 조회, 정해진 로그 요약, 단순 문구·목록 정리, 이미 검증된 반복 확인에 사용한다. 원인 추론이나 운영 변경 판단에는 단독 권장하지 않는다.

### Sol 추론 강도 선택

Sol을 권장할 때는 작업 단계별 reasoning 강도도 함께 제시한다. 더 높은 강도가 항상 더 효율적인 것은 아니므로 재작업 위험과 응답속도를 함께 판단한다.

| Sol 강도 | 속도·자원 특성 | VoiceFlow 권장 작업 |
|---|---|---|
| low | 가장 빠름, 짧은 판단 | 변경 없는 상태 확인, 이미 확정된 명령 실행 결과 요약 |
| medium | 빠른 편, 일반 분석 | 단일 로그 분석, 확정된 테스트 재실행, 작은 문서 수정 |
| high | 정확도와 속도의 균형 | 원인이 확정된 최소 코드 수정, 영향 범위가 제한된 리뷰 |
| xhigh | 깊은 비교와 원인 추적 | 반복 회귀, Git 이분 탐색 설계, 여러 커밋·서비스·기기 비교 |
| max | 매우 깊은 검토, 느림 | xhigh에서도 원인 후보가 충돌하거나 운영·보안 위험이 큰 최종 판단 |
| ultra | 가장 높은 탐색 비용과 시간 | 광범위한 아키텍처·장기 장애의 최종 감사처럼 다른 강도로 해결되지 않는 예외적 작업 |

현재 VoiceFlow의 Golden 기준 확정과 최초 회귀 조사는 **GPT-5.6 Sol · xhigh**를 기본 권장한다. 이유는 STT·번역·화상·외부음성·CI·운영·DEVICE 증거를 함께 비교해야 하지만, 아직 max/ultra가 필요한 증거 충돌 단계까지 확인되지는 않았기 때문이다.

단계가 바뀌면 같은 모델을 고정하지 않는다.

- Golden 후보와 최초 실패가 불명확함: Sol xhigh
- xhigh 조사에서 서로 모순되는 근거가 남음: Sol max
- 정상 SHA와 원인이 확정되고 최소 수정만 남음: Sol high 또는 Terra high
- CI·Docker·정해진 회귀검사 반복: Terra medium
- 상태 조회와 결과 요약: Luna low 또는 medium

모델·강도를 추천할 때 예상 속도, 필요한 추론 깊이, 잘못 판단했을 때의 재작업 위험을 이유로 설명한다. max/ultra는 단순히 더 강하다는 이유로 기본 선택하지 않는다.

다음 조건이면 현재 모델보다 한 단계 높인다.

- 동일 장애가 두 번 이상 재발함
- 세 개 이상 PR·서비스·기기 또는 Provider가 얽힘
- Golden SHA나 실제 DEVICE 결과가 불명확함
- 운영 배포, 인증, Secret, DB, 사용자 데이터에 영향 가능성이 있음
- 이전 수정이 다른 정상 기능을 악화함

다음 조건이 모두 충족되면 Terra 또는 Luna로 낮출 수 있다.

- 실제 정상 기준과 최초 실패 원인이 확정됨
- 변경 파일과 복구 파일이 명확함
- 한 원인만 다루며 운영 위험이 낮음
- 자동검사와 DEVICE 검증 절차가 이미 준비됨

모델 추천은 작업 품질을 낮추기 위한 비용 절감 수단으로 사용하지 않는다. 핵심 장애에서 빠른 모델을 선택해 재작업 위험이 커지면 Sol을 유지한다.

## 구현과 검증

- 기존 구현을 바꿀 때는 추상화/어댑터 또는 기본 OFF 기능 플래그로 신구 구현을 공존시킨다.
- 마이크는 단일 소유자만 사용한다. 전환은 명시적 상태 기계로 하고 병렬 STT를 금지한다.
- 대화 추가는 메시지 영역만 갱신하며 툴바·화상·스크롤 컨테이너 전체 재렌더링을 금지한다.
- 직접입력과 음성은 같은 caption/translation API 계약을 사용한다.
- 연속 생성 패치에서 앞 단계 출력 문자열을 바꾸면 뒤의 모든 `replace`/`must` 앵커 소비자를 추적하고, 최종 생성된 `public/app.js` 계약검사까지 통과시킨다.
- 모달·오버레이 E2E는 표시와 필수 컨트롤을 확인한 뒤 닫기 동작과 DOM 제거를 확인하고 다음 시나리오로 넘어간다.
- 보호된 관리자 화면은 공개 경로의 권한 차단과 내부 배포 자산의 UI 계약을 분리해 검증한다. 리다이렉트된 앱 셸 HTTP 200을 관리자 UI PASS로 간주하지 않는다.
- 번역은 Provider 실응답이 원문과 다를 때만 성공이다. 키 미구성·복호화 실패·Provider 장애를 구분한다.
- 직접입력 번역과 음성/외부음성 STT가 같은 Provider를 쓰더라도 요청 종류와 소비량을 분리 기록한다. 한 기능의 성공을 다른 기능의 성공으로 대체하지 않는다.
- 저장된 Secret 이름이나 암호문 존재를 Provider 구성 완료로 간주하지 않는다. 읽기 검증은 현재 암호화 키와 명시적으로 알려진 이전 키만 순서대로 시도하고, 둘 다 실패하면 코드 패치를 중단해 `SECRET RECOVERY REQUIRED`로 분류한다.
- 암호화 키 변경 시 새 저장은 현재 키만 사용하고, 기존 값은 복호화 성공 후에만 현재 키로 명시적으로 이관한다. 복호화되지 않는 암호문을 덮어쓰거나 키를 자동 생성·교체하지 않는다.
- Provider 사전검사는 `저장 항목 없음`, `암호문 복호화 실패`, `인증 실패`, `모델/요금·쿼터 실패`, `실응답 성공`을 분리해 기록한다. 알려진 키 후보가 모두 실패하면 정확한 과거 키 복구 또는 관리자 화면의 Provider 재저장 없이는 번역/STT를 PASS로 선언하지 않는다.
- SOURCE → 단위/계약 → 프런트 생성 → Docker → CI → DEPLOY → OPERATING → DEVICE 순서로 각각 증거를 남긴다.
- 기준과 후보를 같은 시나리오로 비교한다. 핵심 성공률, 첫 결과 지연, 재렌더 횟수, 마이크 권한 요청 횟수, 참가자/화상 유지가 기준보다 나빠지면 병합하지 않는다.
- 운영 전환은 소수 경로/기능 플래그로 시작하고 실패 시 트래픽만 기준 구현으로 돌린다.

## 배포 후 작동 확인 필수 게이트

- 배포 명령 성공, 컨테이너 실행, Health 200, 정적 자산 존재만으로 완료를 선언하지 않는다.
- 모든 운영 배포 뒤 운영 도메인에서 인증, 핵심 메뉴, 음성 입력, 원문 생성, 선택 언어 번역, 화상, 외부 음성, 저장·재접속을 자동 또는 실제 기기로 확인한다.
- 자동 브라우저 검사는 회원가입·로그인 요청의 실제 응답 완료를 기다리고 고유 계정을 사용한다. 고정 시간 대기만으로 성공을 추정하지 않는다.
- 자동검사로 실제 음성 인식이나 Provider 번역을 증명하지 못한 항목은 DEVICE/PROVIDER UNVERIFIED로 남기고 사용자 기기 확인 전 PASS로 바꾸지 않는다.
- 배포 후검사가 하나라도 실패하면 배포 상태는 PARTIAL 또는 FAIL이며 작업은 미완료다. 실패 원인을 최소 수정한 뒤 재배포와 전체 후검사를 반복한다.
- 후검사가 실행되지 않았거나 GitHub Actions가 생성되지 않은 경우에도 완료 금지다. 배포 트리거를 복구하고 새 운영 검사 증거를 확보한다.

## 복구와 전진 규칙

장애 완화를 위한 마지막 정상 버전 복원은 허용하되 완료로 간주하지 않는다. 복원 후 원인을 격리한 전진 수정과 재발 방지 검사를 추가한다. 정상 기능을 제거하거나 성능을 낮춰 테스트를 통과시키는 “후퇴 해결”은 금지한다.
